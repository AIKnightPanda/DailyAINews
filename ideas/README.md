# 灵感档案

每天从公开渠道收两种东西 —— **有人明说自己缺什么**（需求侧）和**今天上线了什么**
（供给侧）—— 深挖原帖和评论，挑出**真正值得做的**（一天 0 到 3 条），
每条附一小段背景加一句判断，摆在页面最上面的「**精选**」一节。往下是
**点子**（还没做出来的：抱怨、想法、需求）和**产品**（已经做出来的，
不论规模）两个和「精选」平级的大类，各自按**来源**分小节展示，每个来源
都报「展示了几条 / 一共抓了几条」（抓了但一条没展示的来源也照样列出来），
每条一句话说明；内容本身值得多看一眼的条目单独标星（跟它从哪个来源来的
没关系）。
和 AI 简报是**两条并行的管线**，共用设计原则和页面样式，不共用数据。

## 两条规矩

**一、页面上不出现没被读懂的条目。**

一条 Product Hunt 叫「Doop」「Monid」，一条 Reddit 叫「Hey guys」——
光有标题等于没有信息。所以每条展示出来的东西都必须带一句「这是什么」，
说不出来就不展示（它仍然留在 `ideas/raw/` 里，页面上只报个数字）。

**二、页面上只展示「精选」。**

顶部那一节只放判断下来本身有价值的条目，**一天 0 到 3 条是正常的**。
挑不出来就写明「今天没有值得做的」—— 那是诚实的结果，
比凑一条让人浪费一个周末强。没进这一节的都在下面按点子/产品分类的
列表里，可以自己翻。

**三、先判断值不值得做，再想怎么做。**

卡片只有两栏：**背景**（用户是谁、需求/问题是什么、评论区里别人怎么反馈的，
柔性揉成一段话，哪样信息不够就不写那句）和**判断**（值不值得做、为什么）。
2026-09-04 之前是六栏（是什么/谁在要/钱在哪里/已有方案/怎么找到人/判断），
读起来像审计报告。

## 怎么判断「值不值得做」

**不是一张检查表，是对这个点子或产品本身的价值判断。**
2026-09-04 之前这里有一张「四道门槛」表（需求具体/一个人做得完/有人已经在
花钱/找得到这些人），结果判断本身跑偏了——用户的反馈：「值不值得做，是对
这个点子或产品本身的判断，而不是去看是否有这几个元素，这是舍本逐末」。

真正要回答的只有一句：**这件事如果做成了（或者已经做成了），值钱吗？**
下面几件事是找证据的地方，不是打勾的清单——答不上某一条不等于自动出局：

- 需求有多具体：能不能复述出「谁、在什么场景下、卡在哪」
- 钱在哪里：有没有人已经在为它/为替代方案花钱、花时间
- 评论区说明了什么：是不是早有方案、是不是被验证过没人要、有没有报出具体价钱
- 一个人做不做得完：决定「你现在能不能上手」，不决定「这件事本身值不值」
- 找不找得到这些人：说得出具体渠道，还是「发到 App Store」碰运气

**「有没有人已经在花钱」这一条 2026-09-03 曾经补过，原因是一次真实的失误**：
「扫条码查食品召回」需求具体、数据现成、确实没人做、一个人能做完，
但没有任何人在为这件事花钱，获客也只能靠应用商店碰运气——照样不值得做。

> **缺口不等于生意。** 没人做的东西，很多时候正是因为没人肯为它付钱。
> 但这依然是判断价值时要权衡的一个因素，不是四条里必须打勾的一条。

页面：`docs/ideas.html`（GitHub Pages 站点里的 `/ideas.html`，报头右上角可以和简报页互跳）

## 两阶段采集

这是 v2 最重要的结构改动：

```
第一阶段  广度       抓约 120 条候选，只要标题和元信息            fetch-candidates.js
   ↓
预筛      确定性     两条通道各自打分 + 单源配额 → 约 32 条        lib/screen.js
   ↓
第二阶段  深度       只对这 32 条抓正文 + 评论 + 先例              ideas-deepen.js
   ↓
读懂      模型       每条写一句「这是什么」（任务 A）              ideas-style.md
   ↓
判断      模型       从中提炼十条，每条四栏 + 一个结论（任务 B）    ideas-style.md
```

分两阶段的理由很实际：深挖一条要一次带退避的请求，全量做会跑成半小时；
而九成条目连预筛都过不了，为它们花请求纯属浪费。

**评论是这套东西的命根子。** 竞品、已有方案、需求真伪、冷启动难点，
通常都由回帖的人当场点出来 —— 见下面「为什么必须抓评论」。

## 每天怎么跑

```
20:40 UTC  Actions (fetch-ideas.yml)  抓候选 + 抓 Gmail → 提交两个 pending 文件
21:30 UTC  Routine                    归档 → 深挖 → Haiku 翻译与判断 → 拼装 → 建页 → push
```

手动跑一次：

```bash
node scripts/ideas-archive.js         # 抓取 + 归档（约 3–5 分钟，reddit 要退避）
node scripts/ideas-deepen.js          # 预筛 + 深挖（约 4–8 分钟）
node scripts/ideas-extract.js 期号     # 看模型会读到什么
# ……模型产出 ideas/zh/<期号>.json 和 ideas/picks/<期号>.json……
node scripts/link-ideas.js 期号
node scripts/build-ideas-viewer.js
```

## 为什么必须抓评论

2026-09-02 实测，同一天的两个例子：

| 条目 | 只看标题和摘要会怎样 | 评论里写着什么 |
|---|---|---|
| 「截图 30 秒后自动删除」 | 被选成当日第一，推荐花一个周末做 | **「iOS 本来就有这个功能」**，发帖人自己回了「INCREDIBLE! Thank you!」 |
| 「把走过的路线叠在地图上」 | 看起来是个干净的缺口 | 8 条回帖列出 CityStrides、Wandrer、StatsHunters、CoMaps、Samsung Health 五个现成方案，其中一个「就是这个」 |
| 「文献标题批量转句首大写」 | 看起来平平无奇 | 唯一的回答者写了脚本又**弃用了**，因为它把 BDI 转成了 bdi —— 真正的缺口在这句话里 |

标题和摘要判断不了这些。第一条是 v1 真的犯过的错。

## 预筛规则

全部写在 `scripts/lib/screen.js`，**确定性、看得见、改得动**。

供给侧只看两件事：有没有一句话描述（没有就直接不要 —— 「Doop」这种标题
在页面上没法解释），以及热度。下面三组规则只作用于需求侧：

- **出局**：招聘找人、求反馈、自推、调查问卷、加密货币、心理求助、元讨论、
  里程碑分享、口味投票、个人设备故障、停服通知
- **加分**：直说缺口（+6）、在找但没找到（+5）、在用笨办法凑合（+4）、
  有时间成本（+4）、有具体人群（+3）、在换掉现有方案（+3），
  再加互动量和正文长度
- **减分**：要做硬件（−8）、双边市场冷启动（−7）、要牌照合规（−6）、
  要先有人气（−5）、要的是库不是产品（−5）、工程量过大（−4）

**单源配额**是必需的：SoftwareRecs 一天能出 25 条、r/SomebodyMakeThis 只有五条，
纯按分数取前 N 会让一个源吃掉大半名额，而它恰恰是最长尾最技术向的那个。
分数管同源内排序，配额管跨源多样性。

每条的预筛结果（分数、命中了哪些规则、为什么出局）都写进 `ideas/raw/<期号>.json`，
页面上也能看到 —— 规则不透明就没法改。

`ideas-archive.js` 是**累加**的：一天里跑几次都只会把新冒出来的条目追加进当期，
已有条目的编号不动。`--force` 才是真正重来。

## 配 Gmail（一次性，需要你自己做）

IdeaBrowser 每天那封是全清单里质量最高的点子源，而它的公开归档页
（`ideabrowser.com/emails/<日期>`）挂着 Vercel 机器人验证，抓下来只有一页 JS。
**邮件是唯一的入口。**

1. 去 [Google Cloud Console](https://console.cloud.google.com/) 建一个项目
2. 「API 和服务」→ 启用 **Gmail API**
3. 「OAuth 同意屏幕」→ 外部 → 填基本信息 → 把应用**发布为「正式」**
   （停在「测试」状态的话，签发的 refresh token 7 天后作废）
4. 「凭据」→ 创建 OAuth 客户端 ID → 类型选 **桌面应用**
5. 拿到 client id 和 client secret 后，在本地跑一次：

   ```bash
   node scripts/gmail-auth.js <client_id> <client_secret>
   ```

   浏览器里授权，终端会打印出 refresh token。

6. 把三个值填进仓库的 **Settings → Secrets and variables → Actions**：
   `GMAIL_CLIENT_ID` / `GMAIL_CLIENT_SECRET` / `GMAIL_REFRESH_TOKEN`

**这三个值一个都不要提交进仓库 —— 仓库是公开的。**
没配也不影响：`fetch-inbox.js` 会输出一条 error 然后正常退出，榜单那半边照常出。

申请的权限只有 `gmail.readonly`：**只读，不能改、不能删、不能发信。**

### 为什么不用 Gmail 连接器 / MCP

Routine 的沙箱里没有你的 Gmail 凭证，也不该有。而且走 MCP 意味着整封邮件过模型，
既贵又拿不到确定性解析 —— IdeaBrowser 的版式是固定的，正则切得又快又准。

### 隐私

- **只读允许清单里的发件人**（`scripts/idea-sources.js` 的 `NEWSLETTERS`）。
  清单之外的邮件连列都不会列到。
- 落盘前 `sanitize()` 会剪掉页脚、抹掉带订阅者标识的链接、把邮箱地址替换成 `[邮箱]`。
  IdeaBrowser 的退订链接里嵌着一个 JWT（含 contactId / audienceId），
  直接提交到公开仓库等于把它送出去。
- 工作流里还有一道兜底：提交前 grep 一遍疑似凭证的形状，命中就**只丢掉邮件那半边**，
  榜单照常提交。既不泄漏，也不因此丢掉一整天。

## URL 为什么不可能被编造

和简报那条线同一套设计，而且在这里更要紧 —— 简报里编造一条链接，代价是读者点开
发现是死链；灵感清单里编造一条，代价是你信了一个不存在的产品、去调研、去投时间。

1. `ideas-extract.js` 把条目以 `[I12] 标题` 的形式给模型，**不带 URL**，
   连正文里出现的链接也被换成 `[链接]`
2. 模型只写编号，写不出链接
3. `link-ideas.js` 按编号从 `ideas/raw/` 里取真 URL 配回去

## 探针：编号错位是怎么挡住的

译文和精选都带一个 `t` 字段（或译文数组的第一个元素）：**英文原标题的开头一段，
照抄原文**。脚本按前缀匹配来校验。

这最初只是校验，后来发现它还能**定位**：探针必须是标题的前缀，所以只可能匹配上
内容对得上的那一条。于是编号退化成提示，真正说了算的是内容。

2026-09-02 实测，两次都是真事：

| 情况 | 结果 |
|---|---|
| 素材重抓后编号整体偏移，99 条译文里 95 条编号对不上 | 靠探针全部找回，一条没挂错 |
| 精选那份当时**没有**探针，静默指向了另一条帖子 | 页面上毫无异样，headline 直接写错 |

第二条是最坏的一种失败：错了但看不出来。所以精选现在也必须写 `t`，
对不上就整条丢掉并在日志里喊出来。

## 去重

- 每条的 id 由**归一化后的 URL** 决定（剥掉 utm 之类的追踪参数），不由源决定 ——
  同一个东西从 Show HN 和 Product Hunt 各进来一次时才认得出是同一条
- URL 不同、讲同一件事的靠标题指纹认
- 合流时留需求侧那条，被合掉的挂在 `alsoFrom` 里，不丢
- `seen.json` 记跨期指纹，避免同一条连着几天重复出现

## 期号规则（和简报**不一样**）

简报的期号 = 上游 feed 的 `generatedAt`（见根目录 CLAUDE.md）。
**灵感的期号 = 运行当天（Asia/Shanghai）** —— 这个模块没有上游 feed，
没有「这批内容是哪天生成的」这个概念，只有「我这天收到了什么」。

BigIdeasDB 的方法论直接改写了本管线的判断标准：他们分析付费任务的逻辑是

这就是上面「钱在哪里」这条判断依据的由来。

## 还没做的

采集这一层已经完整。往「灵感管理器」还差：

- **决策状态**：`starred / rejected / building`，你唯一需要手写的文件，
